# Implementation Plan: Scientific documentation for every circuit example

**Branch**: `004-circuit-example-docs` | **Date**: 2026-10-18 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/004-circuit-example-docs/spec.md`

## Summary

One Markdown document per distinct example file of the Examples menu (367 entries, 366 distinct
files, so 366 documents), in Portuguese, with LaTeX
equations and optional Mermaid diagrams, under `docs/exemplos/`, plus an index grouped like the
menu that the README links to. Three things keep 366 documents honest: the **index is generated**
from `assets/setuplist.txt` and the documents that exist (a category is "documentado" only when
every example of it has a document), the **component table of each document is generated** from
the example file, and each document lists **checks** (a quantity, a time, an expected value, a
tolerance) that a test runs against the simulator. A small developer tool (`exdocs`) writes the
generated parts and checks everything; the same checks run in `cargo test`. The documents are
written in ten waves by category; every wave leaves the repository green.

## Technical Context

**Language/Version**: Rust, edition 2024 (tool and tests); Markdown with LaTeX (`$…$`, `$$…$$`) and
Mermaid (` ```mermaid `) for the documents

**Primary Dependencies**: none new; reuses `app::examples::parse_setup_list`, the parser and the
solver (`Simulation::run_until`) of the library

**Storage**: files: `docs/exemplos/*.md`, `docs/exemplos/README.md` (index); no database

**Testing**: `cargo test`: unit tests of the checker beside its code; integration test
`tests/example_docs.rs` that reads the real documents; the families builds must stay green (the
test needs the families of the examples it simulates, so it gates each check on the families of
the example, see research R7)

**Target Platform**: documents are read on GitHub and in common Markdown previewers; the tool runs
on the developer's machine

**Project Type**: documentation plus a developer tool inside the existing crate

**Performance Goals**: checking all documents in under 2 minutes in release mode (each check runs
a short simulation)

**Constraints**: GitHub renders LaTeX and Mermaid but not every LaTeX package; stay with plain
math (`\frac`, `\sqrt`, `\omega`, `\mathrm`, `\begin{aligned}`); no images to keep (diagrams are
Mermaid text); no change to the simulator, the example files or the file format

**Scale/Scope**: 366 documents (367 menu entries, one file listed twice); about 40 recurring physical topics; 10 waves

## Constitution Check

*GATE: passed before research and again after design.*

| Principle | Result |
|-----------|--------|
| I Code quality | the tool and tests pass `fmt` and `clippy -D warnings`, with and without `gui` |
| II Test-first | the checker's tests are written first (missing document, orphan, stale table, bad link, bad check, unbalanced LaTeX); the documents themselves are checked by the checker before each wave is accepted |
| III Layered testing | unit tests for parsing and rendering the index; integration test over the real `docs/exemplos/`; error paths tested (each failure mode of the checker has a test) |
| IV Maintainable design | one small module (`src/exdocs/`) with parsing, rendering and checking; the tool is a thin `main`; public items documented; errors are typed `Result`s |
| V Dependencies and docs | no crate added; the README gains the link (public behaviour documented in the same change) |

No violations; Complexity Tracking is empty.

### Source Code (repository root)

```text
└── <example-file-stem>.md   # one per example, e.g. filt-lopass.md
src/exdocs/mod.rs            # setup list → documents; ties the parts together
src/exdocs/front.rs          # front matter of a document
src/exdocs/lint.rs           # sections, LaTeX, Mermaid, links
src/exdocs/index.rs          # status of the categories and the index
src/exdocs/region.rs         # generated regions: components table, navigation line
src/exdocs/checks.rs         # the `verificacoes` of a document, run against the simulator
src/bin/exdocs.rs            # `sync`, `check`, `facts <example>`, `skeleton <example>`
tests/example_docs.rs        # the checks over the real documents
README.md                    # a row in the documentation table linking the index
```

**Structure Decision**: flat folder with the example's file stem as the name (so the mapping from
the menu is one rule); the index carries the categories. Waves are a work plan, not a folder
structure.
